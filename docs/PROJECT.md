# KaigiAI — локальный офлайн-переводчик встреч и диалогов

> 会議 (kaigi) — «встреча / совещание». Приложение слушает речь, в реальном
> времени распознаёт два языка, переводит их «крест-накрест» и ведёт заметки —
> всё **локально на устройстве**, без отправки данных в облако.

Статус документа: черновик дизайна (v0.1). Раздел «Открытые вопросы» в конце.

---

## 1. Видение

Десктопное приложение для живых и онлайн-разговоров между людьми, говорящими на
двух разных языках. Пользователь запускает запись (микрофон и/или системный звук),
приложение распознаёт речь, определяет язык каждой реплики и показывает её вместе с
переводом на противоположный язык в двухпанельном интерфейсе. По завершении —
сохраняет диалог в локальную базу и может сгенерировать краткое AI-саммари.

Главные принципы:
- **Локально по умолчанию, выбор за пользователем.** По умолчанию всё работает на
  устройстве (приватно, офлайн). В настройках пользователь может вместо этого
  подключить внешний/локальный API-провайдер, если ему важнее скорость и качество
  без мощного железа. Выбор приоритета — за пользователем.
- **Минимальная задержка.** Распознавание и перевод почти в реальном времени.
- **Знакомый UX.** Интерфейс максимально близок к современному Claude Desktop.

## 2. Сценарии использования

1. **Очный двуязычный разговор.** Два человека (напр. RU ↔ EN) говорят по очереди;
   приложение показывает оригинал и перевод в реальном времени, помогая понимать
   друг друга.
2. **Онлайн-встреча.** Захват системного звука из Zoom/Teams/браузера — перевод речи
   собеседника на лету.
3. **Диктофон + перевод.** Один пользователь наговаривает текст, получает перевод.
4. **Текстовый ввод.** Можно печатать вручную вместо голоса.
5. **Заметки и итоги.** После разговора — сохранённый транскрипт + AI-саммари
   (ключевые пункты, договорённости / action items).
6. **Экспорт.** Выгрузка диалога в файл (txt / markdown / json) для архива или обмена.

## 3. Функциональные требования

### 3.1 Захват аудио
- Источник: **микрофон** и **системный звук** (Windows: WASAPI loopback).
- Выбор устройства ввода в настройках.
- VAD (детектор голосовой активности) для нарезки потока на реплики и снижения нагрузки.

### 3.2 Распознавание речи (STT)
- Локальный Whisper (whisper.cpp).
- Авто-определение языка **по каждому сегменту** (а не один на весь диалог) —
  чтобы корректно маршрутизировать реплики в две панели.
- Потоковый режим: VAD → чанки → инкрементальная выдача текста.

### 3.3 Двуязычный режим и перевод
- Пользователь задаёт **языковую пару** (напр. Язык A = RU, Язык B = EN).
- Реплика на языке A → переводится на B, и наоборот («крест-накрест»).
- Перевод локальной LLM (llama.cpp).
- **Раскладка — параллельный транскрипт по языкам.** Левая колонка = Язык A,
  правая = Язык B. Каждая реплика — одна **строка-пара**, выровненная по горизонтали:
  оригинал на стороне своего языка, перевод напротив. Исходная (произнесённая)
  сторона помечается индикатором, чтобы было видно направление перевода.

### 3.4 Заметки и саммари
- Транскрипт сохраняется автоматически (оригинал + перевод + таймстемпы).
- По кнопке/в конце — AI-саммари локальной LLM: краткое содержание, ключевые пункты,
  action items.
- (Опционально, позже) ручные пометки пользователя к диалогу.

### 3.5 История диалогов
- Левое меню со списком диалогов, кнопка «Новый диалог».
- Хранение в локальной **SQLite**.
- Переименование, удаление, поиск по диалогам.

### 3.6 Настройки
- Язык интерфейса приложения (i18n).
- Языки по умолчанию (пара A/B).
- Выбор провайдера (**локально / API**), ввод API-ключа и base URL.
- Выбор/смена ML-моделей (STT, перевод/саммари) — удобный менеджер моделей.
- Устройство аудиоввода, источник (микрофон / системный звук).
- Вычислитель: GPU (CUDA) / CPU.
- **Сохранять запись диалога** (Opus) — по умолчанию **выключено** (хранится только текст).
- **Встроенная справка по настройке API** (для нетехнических пользователей):
  пошагово «где взять ключ → что вставить → какую модель выбрать», с рекомендациями
  провайдеров (Groq/Gemini/DeepL) и их бесплатных лимитов. Прямые ссылки на страницы
  получения ключа. Цель — упаковать приложение так, чтобы простой пользователь
  настроил его без посторонней помощи.

### 3.7 Экспорт
- Форматы: txt, markdown, json (минимум). PDF — опционально.
- Состав: оригиналы, переводы, таймстемпы, (опц.) саммари.

## 4. Нефункциональные требования

- **Офлайн-first (в локальном режиме).** При выборе локального провайдера — полная
  работа без интернета (кроме разовой загрузки моделей). В API-режиме интернет/сеть
  требуется по выбору пользователя.
- **Приватность.** Нет телеметрии. В локальном режиме данные не покидают устройство.
  При выборе API-провайдера — явное предупреждение, что данные уходят на внешний/
  указанный эндпоинт.
- **Лицензирование.** Продукт — **open-source под MIT**. Веса моделей **не
  распространяются** (скачиваются пользователем при первом запуске), поэтому лицензии
  моделей — на стороне пользователя; приложение показывает/уважает их условия. Дефолтные
  модели — **Apache-2.0**. Зависимости (Tauri/whisper.cpp/llama.cpp/React/crates) —
  MIT/Apache, совместимы. Перед релизом — собрать NOTICE по третьим сторонам.
- **Производительность.** Реальное время на NVIDIA GPU; деградация на CPU с более
  лёгкими моделями.
- **Кроссплатформенность.** Первый билд — Windows (NVIDIA/CUDA). Архитектура должна
  допускать сборку под Apple Silicon (Metal) без переписывания ядра.
- **Современный UX.** Визуально и по ощущениям близко к Claude Desktop.

## 5. Технологический стек (решено)

> **Решение:** Tauri + Rust-ядро. Ядро проектируется как **сервис** с чистой границей
> «клиент ↔ бэкенд», чтобы тот же код работал и встроенным локально (десктоп), и как
> отдельный сервер (будущий self-host — см. раздел 14).


| Слой | Выбор | Обоснование |
|---|---|---|
| Оболочка/рантайм | **Tauri** (Rust core) | Лёгкий, нативный доступ к аудио, один бинарник, CUDA/Metal через ML-движки |
| UI | **React + TypeScript** (Vite) | Повторяет стек и стиль Claude Desktop |
| STT | **whisper.cpp** через `whisper-rs` | Стандарт локального распознавания; CUDA + Metal; детект языка |
| Перевод + саммари | **llama.cpp** через `llama-cpp-rs` (LLM, напр. Qwen2.5 / Gemma) | Одна модель и переводит, и резюмирует → меньше движков и моделей; CUDA + Metal |
| Аудио-захват | Rust (`cpal` + WASAPI loopback на Windows) | Нативный, низкая задержка, доступ к системному звуку |
| VAD | Silero VAD / webrtcvad | Нарезка потока на реплики |
| Хранилище | **SQLite** (`sqlx` / `rusqlite`) | Локально, надёжно, простая схема |
| i18n | i18next (фронт) | Стандарт для React |

**Почему Tauri+Rust:** нативная производительность ML и веб-уровень UI; лёгкий десктоп;
React-фронтенд переиспользуется в браузере; Rust одинаково хорош как нативное ядро и как
HTTP/WS-сервер (Axum) — прямой путь к self-host. **Почему не Electron:** тяжелее
(~150 МБ), ML через sidecar. **Почему не Python+Qt:** UX-уровень Claude Desktop тяжело
достижим, десктоп-упаковка сложнее.

**Резервный путь:** если понадобится специализированная модель перевода
(NLLB / Opus-MT / ctranslate2) — добавляется опциональный **Python-sidecar**, не
ломая основную архитектуру.

```
┌───────────────┴───────────────────────────▼─────────────────┐
│  Backend (Rust core)                                          │
│                                                               │
│  Audio Capture ──► VAD ──► STT (whisper.cpp) ──► Lang ID      │
│        (mic /                                       │         │
│       loopback)                                     ▼         │
│                                          Router (A↔B)         │
│                                                     │         │
│                                                     ▼         │
│                                   Translate (llama.cpp LLM)   │
│                                                     │         │
│                          ┌──────────────────────────┤         │
│                          ▼                          ▼         │
│                    Summarize (LLM)            SQLite store    │
│                          │                          │         │
│                          └──────────► Export (txt/md/json)    │
└───────────────────────────────────────────────────────────────┘
```

### Принцип: ядро как сервис (под будущий self-host)
Бэкенд-логика (STT, перевод, саммари, хранилище) изолирована за чёткой границей
«клиент ↔ бэкенд» и общается с фронтендом через HTTP/WS-подобный контракт. В десктопе
ядро встроено и слушает localhost; тот же код позже поднимается как Axum-сервер для
развёртывания на сервере компании. Фронтенд (React) не знает, локальный бэкенд или
удалённый — только его адрес. См. раздел 14.

### Поток данных (realtime)
1. Аудио-фрейм → VAD определяет границы речи.
2. Готовый сегмент → whisper.cpp → текст + язык сегмента.
3. Router: язык == A → переводим в B; язык == B → переводим в A.
4. LLM переводит; оригинал и перевод стримятся в обе панели.
5. Реплика пишется в SQLite.
6. По завершении — LLM формирует саммари; доступен экспорт.

## 7. ML-пайплайн: детали и компромиссы

- **Стриминг Whisper.** Whisper не стримит «из коробки». Используем VAD + перекрытие
  чанков (sliding window), чтобы выдавать текст инкрементально. Компромисс
  задержка/точность настраивается размером окна.
- **Детект языка.** Whisper определяет язык на сегмент. В двуязычном диалоге это
  ключ к маршрутизации. Риск: короткие реплики / смешанный код-свитчинг — нужны эвристики.
- **Перевод LLM.** Промпт вида «переведи с A на B, верни только перевод». Плюс — качество
  и контекст; минус — латентность выше, чем у узких MT-моделей. Для слабого железа
  предусмотреть лёгкую модель / fallback на Opus-MT (sidecar).
- **Диаризация спикеров (поэтапно).** Язык ≠ говорящий: два человека могут говорить
  на одном языке, и по языку их не различить. Подход:
  - *MVP:* без диаризации. Опционально — 2-сторонняя атрибуция по **источнику аудио**
    (микрофон = локальный участник, системный звук = удалённый); покрывает 1-на-1.
  - *Этап 3:* настоящая диаризация по голосу — ONNX speaker-embedding через крейт `ort`
    в процессе (фолбэк — сайдкар), для нескольких спикеров на одном языке. Дизайн: §10.6.
  - Спикер хранится как атрибут реплики (`speaker` в схеме) уже с MVP, чтобы добавить
    ML позже без миграции.

## 8. Модель данных (SQLite, черновик)

```sql
conversation(
  id            TEXT PRIMARY KEY,
  title         TEXT,
  lang_a        TEXT,            -- напр. 'ru'
  lang_b        TEXT,            -- напр. 'en'
  speaker_names TEXT,            -- JSON {label -> имя} для переименования спикеров (этап 3, §10.6)
  created_at    INTEGER,
  updated_at    INTEGER
);

message(
  id            TEXT PRIMARY KEY,
  conversation_id TEXT REFERENCES conversation(id),
  source        TEXT,            -- 'mic' | 'system' | 'text'
  detected_lang TEXT,            -- 'ru' | 'en' | ...  (язык оригинала = сторона панели)
  speaker       TEXT,            -- метка спикера; NULL до диаризации (этап 3)
  original_text TEXT,
  translated_text TEXT,
  start_ms      INTEGER,         -- таймстемп от начала записи
  end_ms        INTEGER,
  created_at    INTEGER
);

summary(
  conversation_id TEXT PRIMARY KEY REFERENCES conversation(id),
  content       TEXT,            -- markdown: содержание, пункты, action items
  model         TEXT,
  created_at    INTEGER
);

-- Аудио хранится только если пользователь включил опцию (по умолчанию выкл).
audio_clip(
  message_id    TEXT PRIMARY KEY REFERENCES message(id),
  path          TEXT,            -- путь к Opus-файлу в папке приложения
  duration_ms   INTEGER
);

note(                            -- опционально (ручные пометки)
  id            TEXT PRIMARY KEY,
  conversation_id TEXT REFERENCES conversation(id),
  message_id    TEXT,            -- NULL = заметка ко всему диалогу
  content       TEXT,
  created_at    INTEGER
);

setting(key TEXT PRIMARY KEY, value TEXT);  -- язык UI, модели, устройства и т.д.
```

## 10. Управление моделями

- Каталог поддерживаемых моделей (STT и LLM) с метаданными: размер, язык, лицензия,
  требования (CPU/GPU/VRAM).
- **Доставка — скачивание при первом запуске** с официального источника (HuggingFace)
  с прогрессом; хранение в пользовательской папке приложения. Веса **не бандлятся** в
  установщик (лёгкий инсталлятор + обходим вопросы распространения). Дефолтные локальные
  модели — с **пермиссивной лицензией (Apache-2.0)**.
- Переключение активной модели в настройках без перезапуска (по возможности).
- Индикация совместимости с железом пользователя.

### 10.1 Железные тиры (пресеты)

Whisper и LLM держатся в VRAM **одновременно** (realtime), поэтому бюджет считается
на обе модели сразу (whisper.cpp + llama.cpp, Q4/Q5_K_M):

| Тир | VRAM | Пример GPU | Whisper | LLM | Бюджет |
|---|---|---|---|---|---|
| **Low** | 6 ГБ | GTX 1060, RTX 2060 | small | Qwen2.5-3B Q4 | ~3.7 ГБ |
| **Mid** | 10–12 ГБ | RTX 3080 (desktop), 2060-12G | medium | Qwen2.5-7B Q4 | ~8 ГБ |
| **High** | 16 ГБ+ | **RTX 3080 Ti Laptop** | large-v3 | Qwen2.5-7B Q5 | ~10.5 ГБ |
| CPU-fallback | — | без CUDA | base/small | Qwen2.5-3B Q4 | RAM |

Заметки:
- Pascal (1060) — нет Tensor cores, LLM медленнее; для слабых карт держать CPU-fallback.
- Ноутбучные GPU делят тепловой бюджет с CPU → при троттлинге опускаться на тир ниже;
  для длинных сессий — питание от сети.

### 10.2 Дефолт разработки (целевая машина)

RTX 3080 Ti Laptop, 16 ГБ → **Whisper large-v3 + Qwen2.5-7B-Instruct (Q5_K_M)**.
Запас ~5 ГБ под KV-cache, длинный контекст и эксперименты с 14B.

### 10.3 Режимы провайдеров (локально / API)

В настройках пользователь выбирает источник ИИ — это абстракция `Provider` с двумя
реализациями (отдельно для STT и для LLM, можно смешивать):

1. **Локальный режим (sidecar-серверы)** — `whisper.cpp` + `llama.cpp` запускаются как
   **отдельные процессы**, а приложение общается с ними по HTTP через тот же
   `ApiProvider` (OpenAI-совместимые `/v1/audio/transcriptions` и `/v1/chat/completions`
   на `localhost`). Пользователь устанавливает серверы сам и указывает в настройках путь
   к `whisper-server` и `llama-server` + пути к моделям (.bin/.gguf); приложение спавнит
   их с нужными флагами, делает health-check и глушит при выходе.
   - **Почему не in-process** (`whisper-rs` + `llama-cpp-2` в одном бинаре): оба `-sys`-крейта
     статически вкомпиливают **свою копию `ggml`** → дублирующиеся символы → ошибка
     линковки `LNK2005/LNK1169` на Windows (а `/FORCE:MULTIPLE` рискует ABI-рассинхроном
     из-за разных версий ggml). Отдельные процессы устраняют конфликт как класс, дают
     изоляцию (краш C++ не роняет приложение), GPU-сборку выбирает пользователь, и нам
     **не нужно компилировать** whisper/llama (никакого CMake/CUDA/bindgen в нашей сборке).
   - Порты: фиксированные по умолчанию (8771 whisper / 8770 llama) с фолбэком на свободный.
2. **ApiProvider** — **OpenAI-совместимый** клиент: `base_url` + `api_key` + имя модели.
   Один код покрывает сразу:
   - облачные API (Groq, Gemini, OpenAI, Mistral…),
   - локальный сервер на той же машине/в LAN (**Ollama / LM Studio / vLLM**),
   - корпоративный/self-hosted эндпоинт,
   - **локальные sidecar-серверы** из п.1 (тот же код, `base_url` указывает на `localhost`).

Зачем два режима: гарантировать мощный GPU нельзя; на слабом железе накопительная
задержка ломает realtime. API-режим даёт скорость/качество без локальных ресурсов —
ценой приватности (показываем предупреждение).

Бесплатные API для разработки и слабых машин (лимиты/политики данных проверять):
Groq (Whisper large-v3 + быстрые LLM), Gemini Flash, DeepL Free (перевод, есть JP),
Cloudflare Workers AI, OpenRouter `:free`. Self-hosted LibreTranslate — офлайн-перевод.

### 10.4 Качество перевода и выбор модели (рекомендация)

Приложение рассчитано на **много языковых пар** и распространение широкой аудитории,
у которой **слабый ПК — норма**. Отсюда разделение:

**Power-user (сильный GPU, как 3080 Ti 16 ГБ):**
- Минимум — **Qwen2.5-7B (Q5)**: уверенно держит смысл, контекст, регистр речи.
- Для сложных пар (напр. JP↔RU) — **Qwen2.5-14B (Q4)**, влезает в 16 ГБ, заметно сильнее.
- **3B не использовать** на таком железе — только Low-тир/fallback.

**Массовый пользователь (слабый ПК):**
- Локальная 3B даёт лишь «суть», по редким парам качество посредственное, особенно
  не-топовые языки Qwen. Честно выставляем ожидания в UI.
- Практичный путь по умолчанию для слабых машин — **API-режим** (бесплатные тиры:
  Groq для STT+LLM, DeepL Free для перевода) → хорошее качество без GPU.

**Влияет на «передачу смысла» помимо размера модели:**
- **Квантование:** на сильном железе брать **Q5** (почти без потерь); Q4 заметнее режет 3B.
- **Контекст:** кормить LLM предыдущими репликами, не переводить фразу изолированно.
- **Границы фраз:** дожидаться конца предложения через VAD — иначе перевод по обрывкам
  ломает смысл (компромисс задержка/качество).
- **JP↔RU** и другие низкоресурсные пары — тестировать отдельно; при критичности
  качества подключать **DeepL** (через абстракцию провайдеров; STT/перевод/саммари
  можно смешивать — напр. локальный whisper + DeepL-перевод + локальное саммари).
- **STT для мультиязычности:** whisper large-v3 покрывает ~99 языков; на слабом ПК
  придётся опускаться до small/base (теряя точность по не-английским) → ещё аргумент
  за API-STT (Groq) для массовых пользователей.

### 10.5 Установка локального режима (sidecar-серверы)

Локальный режим требует, чтобы пользователь сам поставил серверы `whisper.cpp` и
`llama.cpp` и скачал модели. Приложение их **не качает и не компилирует** — только
запускает по указанным в настройках путям (см. 10.3). Те же ссылки продублированы
прямо в настройках рядом с полями путей (кнопки «↓»), чтобы поставить всё не выходя
из приложения.

**1. Серверы (исполняемые файлы).** Скачать готовые сборки под Windows:
- `whisper-server.exe` — релизы whisper.cpp:
  <https://github.com/ggml-org/whisper.cpp/releases>
- `llama-server.exe` — релизы llama.cpp:
  <https://github.com/ggml-org/llama.cpp/releases>

  Брать **CUDA-сборку**, если есть GPU NVIDIA (иначе обычную CPU-сборку). Распаковать
  в любую папку, напр. `C:\whisper.cpp\` и `C:\llama.cpp\`.

**2. Модели.**
- Whisper (GGML `.bin`): <https://huggingface.co/ggerganov/whisper.cpp/tree/main> —
  напр. `ggml-large-v3.bin` (лучшее качество) или `ggml-small.bin` (для слабого ПК).
- LLM (GGUF): <https://huggingface.co/Qwen/Qwen2.5-7B-Instruct-GGUF/tree/main> —
  напр. `qwen2.5-7b-instruct-q5_k_m.gguf` (см. рекомендации по выбору в 10.4).

  Сохранить модели куда удобно, напр. `C:\models\`.

**3. Настройки приложения** (раздел «ИИ-провайдер» → режим «💻 Локально»): указать
- путь к `whisper-server.exe` и к модели Whisper (`.bin`);
- путь к `llama-server.exe` и к модели LLM (`.gguf`);
- «Слои на GPU» (`-ngl`): `0` — только CPU; больше нуля — выгрузка слоёв на GPU
  (чем больше, тем быстрее, пока хватает VRAM).

После этого приложение само поднимает оба сервера на `localhost` (порты 8771/8770 с
фолбэком), делает health-check перед записью и глушит их при выходе. Аудио и текст
никуда не уходят с устройства.

### 10.6 Диаризация спикеров (реализовано)

Язык ≠ говорящий: два человека на одном языке по A/B-маршрутизации не различимы.
Помечаем каждый VAD-сегмент меткой спикера. Границы реплик уже даёт VAD —
диаризации остаётся только присвоить ярлык.

- **Движок.** ONNX-модель speaker-embedding (напр. wespeaker / 3D-Speaker, ~10–25 МБ),
  загружается **в процессе** через крейт `ort` (ONNX Runtime). Конфликта символов
  ggml нет — у ORT свой рантайм. Если нативная линковка под Windows/MSVC заупрямится —
  **фолбэк на отдельный сайдкар** диаризации (по образцу whisper/llama).
- **Доставка модели.** Не бандлим: пользователь скачивает ONNX-файл сам и указывает
  путь в Settings (тот же паттерн, что whisper `.bin` / llama `.gguf`). Пустой путь →
  диаризация выключена (`NullDiarizer`, `speaker = NULL`, как сейчас).
- **Кластеризация.** Онлайн, без знания числа спикеров заранее: на сегмент считаем
  embedding, сравниваем по косинусной близости с центроидами известных спикеров; выше
  порога → тот же, иначе новый. Центроид обновляем скользящим средним. Состояние —
  **per-session** (живёт внутри одной записи), чтобы «Speaker 1» не путался между беседами.
- **Метки.** Технические, стабильные в рамках беседы: `Speaker 1 / Speaker 2 / …`,
  пишутся в `message.speaker`.
- **Переименование.** Пользователь один раз задаёт человекочитаемое имя
  (`Говорящий А → Масаки`); оно **персистентно на беседу**. Хранится как JSON-карта
  `label → имя` в новой колонке `conversation.speaker_names`. Применяется при рендере и
  при **экспорте** (в выгрузке подставляется имя). Технические метки в `message.speaker`
  не меняются — переименование чисто презентационное, кластеризацию не ломает.
- **Интеграция.** `provider/diarize.rs` (trait `Diarizer` + `NullDiarizer` / `OnnxDiarizer`);
  вызов в пайплайне записи после STT, до перевода; диаризатор создаётся per-session в
  `Recorder::start`. UI: инлайн-редактор имени по клику на бейдж спикера.
- **Статус.** Реализовано и собрано. Крейт `ort` 2.0.0-rc.9 линкуется в процессе под
  Windows/MSVC (фолбэк-сайдкар не понадобился). Протестированная модель —
  `wespeaker_en_voxceleb_resnet34_LM.onnx` (~25 МБ). Путь задаётся в Settings; пустой
  путь → диаризация выключена.

## 12. Решённые вопросы

- **Раскладка панелей.** Параллельный транскрипт по языкам: две колонки, каждая
  реплика — выровненная строка-пара (оригинал + перевод напротив), исходная сторона
  помечена. *(Решено.)*
- **Спикеры.** Атрибут `speaker` в схеме с MVP; диаризация — этап 3: ONNX-embedding
  через `ort` в процессе (фолбэк — сайдкар), модель докачивается отдельно (как
  whisper/llama). Метки `Speaker N` стабильны в рамках беседы; переименование
  персистентно на беседу (`conversation.speaker_names`), применяется в UI и экспорте.
  В MVP опционально 2-сторонняя атрибуция по источнику аудио. Дизайн: §10.6. *(Решено.)*
- **Модели и железные тиры.** Low/Mid/High пресеты; целевая машина (3080 Ti Laptop,
  16 ГБ) → Whisper large-v3 + Qwen2.5-7B Q5. См. раздел 10. *(Решено.)*
- **Режимы ИИ.** Абстракция `Provider`: локально (whisper.cpp+llama.cpp, авто-скачивание)
  ИЛИ API (OpenAI-совместимый base_url+ключ — облако/Ollama/LM Studio/корп.сервер).
  Выбор за пользователем. См. раздел 10.3. *(Решено.)*
- **Исходное аудио.** По умолчанию **не хранится** (только текст — экономия диска +
  приватность). Переключатель «сохранять запись диалога» (формат Opus). *(Решено.)*
- **Доставка моделей.** **Скачивание при первом запуске** с официального источника
  (HuggingFace) — лёгкий установщик, не распространяем веса. Дефолтные локальные модели
  выбирать с пермиссивной лицензией (Apache-2.0). *(Решено.)*
- **Альтернатива LLM.** Каталог моделей поддерживает несколько; дефолт Qwen2.5,
  Gemma-2-9B опционально для сравнения; финал — по тестам. *(Решено.)*
- **Стек.** **Tauri + Rust-ядро**, спроектированное как сервис (граница клиент↔бэкенд)
  под будущий self-host. React-фронтенд переиспользуется в вебе. См. разделы 5, 6, 14.
  *(Решено.)*
- **Лицензия.** Продукт open-source под **MIT**. Веса не распространяются (скачивание
  пользователем), дефолты — Apache-2.0, зависимости MIT/Apache. Раздел 4. *(Решено.)*

## 14. Будущее направление: веб и self-host

Стратегическая цель — дать возможность пользователям и компаниям **разворачивать
бэкенд на своих серверах** и работать через браузер. Архитектура закладывается под это
уже сейчас (раздел 6, «ядро как сервис»):

- **Бэкенд как отдельный сервис.** Десктоп встраивает то же Rust-ядро; для self-host
  оно поднимается как **Axum HTTP/WS-сервер**. Логика не дублируется.
- **Фронтенд переиспользуется.** React-UI работает и в Tauri-webview, и в обычном
  браузере; знает только адрес бэкенда.
- **Self-host = частный случай провайдеров.** Компания с GPU поднимает сервер; клиенты
  (десктоп или браузер) указывают его `base_url` — это уже спроектированный
  `ApiProvider` (раздел 10.3). Корпоративный сценарий выпадает почти бесплатно.
- **Оговорка по аудио в браузере.** Системный звук (WASAPI loopback) — нативная
  десктоп-фича; в браузере доступны только микрофон и звук вкладки (`getDisplayMedia`).
  Веб-версия по захвату звука будет слегка урезана относительно десктопа.
- **Многопользовательность (позже).** Серверный режим потребует аутентификации и
  изоляции данных по пользователям/организациям — вне текущего MVP, но граница
  «клиент↔бэкенд» это не блокирует.
